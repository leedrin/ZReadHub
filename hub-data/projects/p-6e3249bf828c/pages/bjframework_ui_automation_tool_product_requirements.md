# BJFramework UI Prefab 自动化工具 - 产品功能需求文档

## 1. 核心目标

*   **自动化绑定**：拖入 UI Prefab 资源后，自动扫描其下的指定类型组件。
*   **描述文件生成/更新**：根据收集到的组件信息，自动生成或更新程序绑定所需的 C# 描述文件（如 [`CatchFishUICtrlDesc.cs`](Assets/GameProject/Scripts/Runtime/GameView/UI/CatchFish/CatchFishUICtrlDesc.cs)）。
*   **高效用户体验**：提供便捷的 Editor 工具界面，支持拖拽、预览、一键导出等功能。
*   **规范化支持**：结合 [`GameObject`](https://docs.unity3d.com/ScriptReference/GameObject.html) 命名规范（如 `@_btn_xxx`）来自动生成 C# 变量名、别名和注释。
*   **增量更新**：当 Prefab 已添加描述文件时，应以该描述文件为基准进行增量更新，保留已有字段名，仅添加新增组件。
*   **架构可扩展性**：引入模板引擎系统和插件化架构，提升工具的可维护性、扩展性和灵活性。

## 3. 详细功能描述

### 3.1 双模式组件收集 (A1)

工具应提供以下三种收集模式：

1.  **规范模式**:
    *   **行为**: 仅收集名称以特定前缀（默认为 `@`）开头的 `GameObject`。
    *   **示例**: `@Btn_Confirm` 会被收集，而 `ConfirmButton` 会被忽略。
    *   **适用场景**: 美术资源已严格遵循命名规范的项目。

2.  **回退模式**:
    *   **行为**: 忽略 `GameObject` 的命名，收集所有在配置列表中指定的组件类型（如 `Button`, `Text`, `Image`）。
    *   **示例**: `ConfirmButton` 上的 `Button` 组件会被收集。
    *   **适用场景**: 处理历史遗留的、未规范命名的 Prefab。

3.  **混合模式**:
    *   **行为**: 结合规范模式和回退模式。首先收集所有规范命名的组件，然后对剩余的 `GameObject` 应用回退模式。
    *   **适用场景**: 推荐使用，能最大程度地兼容各种情况。

### 3.2 智能命名策略 (A2)

在回退模式下，工具应支持以下命名策略来生成 C# 变量名：

1.  **节点名 + 类型后缀**: `ConfirmButton` → `m_ConfirmButtonBtn`
2.  **仅节点名**: `ConfirmButton` → `m_ConfirmButton`
3.  **类型前缀 + 节点名**: `ConfirmButton` → `m_BtnConfirmButton`
4.  **智能模式 (推荐)**: `ConfirmButton` → `m_ConfirmBtn` (自动识别并移除节点名末尾的类型关键词)

### 3.3 特殊组件额外字段导出 (A4)

工具应具备插件化的能力来处理特殊组件，自动提取其额外数据并生成常量字段。

*   **示例 1: `AdvanceUIStateController`**
    ```csharp
    // 自动生成的代码
    public static readonly List<string> m_catchFishUIStateList = new List<string>
    {
        "Close", "Show", "Fishing", "Result"
    };
    ```

*   **示例 2: `Dropdown`**
    ```csharp
    // 自动生成的代码
    public static readonly List<string> m_difficultyOptions = new List<string>
    {
        "简单", "普通", "困难", "专家"
    };
    ```

### 3.4 增量更新工作流 (A5)

1.  **检测**: 当用户选择一个已绑定 `UICtrlDesc` 脚本的 Prefab 时，工具自动检测并解析该脚本。
2.  **匹配**: 工具遍历 Prefab 中的组件，计算其 `AliasPath`，并与已存在脚本中的字段进行匹配。
3.  **合并**:
    *   **匹配成功**: 保留脚本中已有的字段名，标记为“已有”。
    *   **匹配失败**: 将其识别为新增组件，按命名规范生成新字段名，标记为“新增”。
4.  **生成**: 在更新脚本时，保留“已有”字段，添加“新增”字段，并移除 Prefab 中已不存在的字段。

### 3.5 模板引擎系统 (E1)

*   **接口**: 定义 `ITemplateEngine` 接口，支持从模板文件或字符串生成代码。
*   **语法**: 采用类似 Liquid 的简洁语法 (`{{variable}}`, `{{#each}}...{{/each}}`)。
*   **管理**: 提供 `TemplateManager` 来管理模板文件，支持项目级、用户级和默认模板的优先级加载。
*   **数据模型**: 定义清晰的模板数据模型（如 `DescriptionFileTemplateModel`），将业务逻辑与模板渲染解耦。

### 3.6 插件化特殊组件处理 (E2)

*   **接口**: 定义 `ISpecialComponentProcessor` 接口，包含 `CanProcess`, `ProcessComponent`, `ValidateResult` 等方法。
*   **管理**: 提供 `SpecialComponentPluginManager` 来自动发现、注册和调用所有插件处理器。
*   **扩展性**: 第三方开发者可以创建独立的程序集来实现此接口，从而扩展工具的功能。

## 4. 非功能性需求

| 类别             | 需求描述                                                                                                                                                                                                                                                            |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **性能**         | 扫描大型 Prefab（包含数百个组件）时，UI 响应时间不应超过 2 秒。代码生成操作应在 1 秒内完成。                                                                                                                               |
| **易用性**       | 工具界面应直观，核心操作（拖入 Prefab -> 收集 -> 生成）应在 3 次点击内完成。提供清晰的状态反馈和错误提示。                                                                                                                               |
| **可维护性**     | 代码结构清晰，模块间低耦合。核心逻辑与模板、插件分离，便于未来修改和扩展。                                                                                                                                            |
| **可扩展性**     | 通过配置文件、模板系统和插件接口，无需修改核心代码即可支持新的组件类型、命名规范和代码生成格式。                                                                                                                                |
| **健壮性**       | 能处理异常情况，如损坏的 Prefab、格式错误的描述文件、命名冲突等，并提供友好的错误提示，而不是崩溃。                                                                                                                            |
| **向后兼容性**   | 新版本工具应能处理旧版本生成的描述文件，并在可能的情况下进行平滑升级。                                                                                                                                                |

## 5. 用户故事与工作流

### 5.1 故事 1: 从零创建新 UI 界面

**作为** 一名 UI 开发者，
**我想要** 创建一个新的 UI 界面，
**以便于** 快速生成所有必要的绑定代码。

**工作流**:
1.  美术制作了一个 `NewFeatureUI.prefab`。
2.  我打开 **UI Prefab Automation Tool**。
3.  我将 `NewFeatureUI.prefab` 拖入工具的 Prefab 输入区。
4.  我选择 **混合模式**，并点击 **“一键收集组件”**。
5.  工具列出了所有组件，我检查并微调了几个字段的中文描述。
6.  我点击 **“生成/更新描述文件”**。
7.  工具在指定目录下生成了 `NewFeatureUIUICtrlDesc.cs` 文件。
8.  我将该脚本添加到 Prefab 上，完成绑定。

### 5.2 故事 2: 迭代更新现有 UI 界面

**作为** 一名 UI 开发者，
**我想要** 在一个已有的 UI 界面上添加新功能，
**以便于** 只生成新增组件的代码，而不影响我之前手动修改过的字段名。

**工作流**:
1.  美术在 `ExistingUI.prefab` 上新增了两个按钮。
2.  我打开 **UI Prefab Automation Tool**，并选择 `ExistingUI.prefab`。
3.  工具自动检测到 `ExistingUIUICtrlDesc.cs` 文件的存在。
4.  我点击 **“一键收集组件”**。
5.  工具的组件列表中，原有的字段显示为 **[已有]**（绿色），新增的两个按钮显示为 **[新增]**（黄色）。
6.  状态栏显示：“总组件: 20 已有: 18 新增: 2”。
7.  我确认无误后，点击 **“生成/更新描述文件”**。
8.  工具更新了 `ExistingUIUICtrlDesc.cs`，保留了所有原有字段，并添加了两个新字段。

## 6. 未来考虑与扩展方向

*   **UIController & UITask 生成**: 在 `UICtrlDesc` 的基础上，进一步生成 `UIController` 和 `UITask` 的骨架代码，实现更完整的自动化流程。
*   **多语言支持**: 在生成 `Header` 属性时，支持从配置文件中读取多语言翻译。
*   **与版本控制系统集成**: 在生成文件前，检查文件是否被修改，提醒用户提交代码。
*   **命令行接口**: 提供 CLI 支持，以便在 CI/CD 流程中集成自动化检查和生成。
