# Wiki Hub 渲染偏差问题分析与整改计划（2026-05-10）

## 1. 问题现状

当前 `Wiki Hub` 已实现“项目聚合入口 + 阅读页基本可用”，但在“复刻 zread 门户与阅读体验”目标上存在明显差距，主要表现为：

1. Markdown 呈现风格与目标不一致  
- 标题、段落、列表、表格、引用块、间距、字体层级均有偏差。  

2. Mermaid 图与代码块体验不一致  
- Mermaid 在部分页面出现渲染异常或样式突兀。  
- 代码块虽可显示，但配色、间距、可读性、语言标签/高亮风格与目标页面不一致。  

3. 阅读器结构不一致  
- 当前阅读页缺失目标样式中的完整文档导航联动（目录树、页内大纲锚点、滚动定位一致性）。  

4. 视觉设计系统不一致  
- 当前主题色、背景、边框、阴影、排版 token 与 zread 目标页面差异较大，导致整体“门户感”不足。

## 2. 原因分析（根因）

### 2.1 渲染链路根因

当前实现采用 `marked + 自定义 renderer + innerHTML` 的轻量方案，属于“能展示内容”的最小实现。  
目标 zread 页面是“组件化渲染 + 统一文档样式体系（prose/token/code theme）”，两者架构层级不同，导致不是单点修复能补齐。

### 2.2 样式系统根因

当前 `hub/styles.css` 是手写样式集合，没有完整映射 zread 页面中使用的：

1. 设计 token（background/foreground/border/scrollbar 等）  
2. 文档排版体系（prose 规则）  
3. 代码与图表风格体系（pre/code/mermaid 统一策略）

因此即使单个块可渲染，整体视觉仍不接近目标。

### 2.3 交互结构根因

当前 Reader 结构是“项目列表 + 正文”的简化布局，尚未建立：

1. 项目目录树与正文 slug 的强关联  
2. 页内标题锚点生成与滚动同步  
3. 大纲点击定位一致性与去重机制

### 2.4 兼容性根因

Markdown 生态库版本变化（如 `marked` 新版 token 参数）与业务逻辑耦合，容易触发 `[object Object]` 等兼容问题。  
说明当前渲染层缺少“库版本适配隔离”。

## 3. 解决方案（目标态）

## 3.1 总体方案

将阅读渲染从“轻量直出”升级为“统一文档渲染管线”，分三层治理：

1. 渲染层：统一 Markdown AST/HTML 输出策略（含 code/mermaid/表格/引用块）  
2. 主题层：建立 zread 对齐的 CSS token + prose 规则  
3. 导航层：重建 Reader 的目录/大纲/锚点联动

## 3.2 技术方案细化

### A. Markdown 渲染层整改

1. 封装 `MarkdownRenderer`，隔离三方库 API 差异。  
2. 规范 code block 输出结构（language class、容器 class、可扩展 metadata）。  
3. Mermaid 采用统一节点协议与渲染生命周期（渲染前占位、渲染后校验、失败回退）。

### B. 视觉系统整改

1. 建立 `zread-like tokens`：背景、前景、边框、强调色、滚动条等。  
2. 引入/复刻 `prose` 级排版规则，统一正文语义样式。  
3. 重做 code/inline code/blockquote/table 样式，保证可读性与接近度。  
4. Mermaid 容器颜色与正文主题联动，避免“深色块突兀”。

### C. Reader 交互整改

1. 恢复并标准化“项目目录树 -> slug 跳转”。  
2. 增加页内大纲（由 `h1-h3` 自动生成）。  
3. 去重规则：全局目录与页内大纲职责分离，避免重复展示。  
4. 锚点滚动与高亮同步，修复定位偏差。

### D. 质量保障

1. 建立渲染回归样例集（含 mermaid、复杂代码块、表格、中文标题、深层列表）。  
2. 建立视觉验收清单（字体、间距、色彩、边框、阴影、滚动、移动端）。  
3. 每次修改后进行“目标页对照截图检查”。

## 4. 后续修改计划（分阶段）

## 阶段 1：稳定性修复（P0）

目标：先确保“内容永远正确显示”。

1. 固化 markdown 渲染适配层，消除 `[object Object]` 类兼容问题。  
2. 固化 mermaid 渲染流程与 fallback。  
3. 确保代码块、表格、引用块稳定显示。

交付物：
- 渲染适配模块  
- 样例页回归通过记录

## 阶段 2：视觉对齐（P1）

目标：显著接近 zread 阅读观感。

1. 重构 `styles.css` 为 token + prose 两层。  
2. 对齐正文 typography（字号、行高、段落间距、标题层级）。  
3. 对齐 code/mermaid/table 样式。  
4. 修正门户卡片视觉细节（圆角、阴影、边框、留白）。

交付物：
- 新版视觉样式文件  
- 对比截图（当前 vs 目标）

## 阶段 3：导航与交互对齐（P1）

目标：实现“结构和交互行为”接近 zread。

1. 目录树与 slug 路由双向同步。  
2. 页内大纲自动生成与定位。  
3. 去掉重复大纲展示，统一单一信息来源。  
4. 滚动联动与当前章节高亮。

交付物：
- Reader 导航重构  
- 跳转/滚动验收用例

## 阶段 4：验收与收口（P0）

目标：可发布、可持续维护。

1. 建立验收文档：功能、视觉、兼容、性能。  
2. 完成 Windows/macOS 启动脚本联调回归。  
3. 输出已知限制与后续增强项（例如全文检索、主题切换增强）。

交付物：
- 最终验收报告  
- 发布说明与回滚说明

## 5. 验收标准（本次整改）

满足以下条件视为整改完成：

1. Mermaid、代码块、表格在目标示例页面均正确显示，不出现 `[object Object]`。  
2. Reader 页面不存在重复大纲展示，跳转锚点准确。  
3. 门户与阅读页视觉风格与目标明显接近（排版、配色、卡片、边框、阴影）。  
4. 从任一项目入口进入后，展示的页面内容与项目 wiki 数据源一致。  

## 6. 风险与应对

1. 三方库升级导致渲染行为变化  
- 应对：渲染适配层隔离 + 锁版本策略 + 回归样例。  

2. 不同项目 markdown 语法差异大  
- 应对：增加异常语法 fallback 与告警输出。  

3. 样式复刻过深导致维护成本上升  
- 应对：优先“体验对齐”而非逐像素复制，保留可维护 token 结构。
